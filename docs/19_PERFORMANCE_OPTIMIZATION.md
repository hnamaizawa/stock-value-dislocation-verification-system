# v0.6.58 大規模データ時の性能最適化

## 背景

データ更新後に Python の CPU 利用率が高い状態が続き、画面表示や別画面への遷移に長時間かかる問題を改善する。

## 原因と対策

1. `load_config()` から自動ルール学習を暗黙実行していたため、Streamlit の通常再実行でも履歴署名確認や、更新直後には学習本体が走り得た。
   - 通常の設定読込は保存済みルールのオーバーレイだけに限定する。
   - 重いルール学習は `run_real_pipeline()` のデータ更新時に明示的に1回だけ実行する。

2. ルール学習の将来リターン計算が、各銘柄ごとに全株価 DataFrame をフィルタしていた。
   - 株価を最初に銘柄コード別へ1回だけグループ化し、30/90/180日後の照合では直接参照する。

3. データ更新時に特徴量の集約を、特徴量スナップショット保存と定量判定で重複計算していた。
   - `prepare_quantitative_universe()` を1回だけ実行し、同じ DataFrame をスナップショット保存と条件判定で再利用する。

4. Streamlit の大規模 curated bundle を `st.cache_data` で保持すると、画面再実行や新規セッションで大きな DataFrame のシリアライズ／コピーが発生する。
   - 読み取り専用の bundle を `st.cache_resource` でプロセス内共有し、画面遷移や新しいブラウザタブでも同じオブジェクトを再利用する。
   - データ更新成功時には従来どおり `_load_bundle.clear()` で明示的に破棄する。

## 不変条件

- 画面遷移・条件変更だけでは J-Quants を取得しない。
- 画面遷移・通常の `load_config()` ではルール学習本体を実行しない。
- データ更新1回につき、定量特徴量の全銘柄集約は1回だけ行う。
- ルール学習の30/90/180日実績照合で、銘柄ごとに全株価表を再走査しない。
- 学習済みルールの安全境界、out-of-sample 検証、ロールバック仕様は変更しない。
- SBI証券への自動ログイン・注文送信は引き続き行わない。
